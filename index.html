Why it exists

Job hunting is a copy-paste loop.

Searching, re-reading listings, rewriting the same letter, nudging the CV, remembering who you applied to. The repetitive 80% is exactly what software is good at — as long as the human keeps the 20% that actually matters.

1 search boards for the same role
2 re-read near-identical listings
3 rewrite the cover letter, again
4 tweak the CV to match keywords
5 log it in a spreadsheet somewhere
↳ automated — you just review & click Apply

Keep the human in control

No auto-submit, ever. The agent stops at “ready to send.”

Never invent a credential

The LLM can rephrase, but grounding guards forbid it from claiming a skill you don't have.

Run on a student budget

Free academic LLM endpoint, a public jobs API, and Supabase's free tier. No paid APIs anywhere.

The crew

Four focused agents, one clear job each.

Cooperating single-responsibility classes built with dependency injection — CrewAI in spirit, plain testable Python in practice. Each hands its output to the next.

◎
01 · SCOUT

The Scout

Fetches and normalizes job listings from the Bundesagentur für Arbeit API (JSearch as optional fallback), dedupes them, and persists to a shared pool.

search prefs → jobs
▨
02 · MATCHER

The Matcher

Two-stage retrieval: cheap pgvector cosine similarity narrows hundreds of jobs to a top-N, then a per-job LLM writes the score, matched skills, and gaps.

profile + jobs → match scores
✎
03 · WRITER

The Writer

Generates a tailored cover letter (EN/DE) and a CV variant, then exports both as .docx. Highlighted skills are a strict subset of your real ones.

top match → application + files
◈
04 · TRACKER

The Tracker

Enforces a forward-only lifecycle state machine, schedules 7-day follow-ups, and owns the GDPR right-to-erasure that wipes your data and artifacts.

status change → updated application

How it works

The decisions that keep an LLM honest.

A Next.js frontend and a FastAPI backend over the agent core, with Supabase (Postgres + pgvector) for storage and auth. Five design choices do the heavy lifting.

Typed I/O

Every LLM response is a strict Pydantic schema

With extra="forbid", the model physically cannot inject stray fields. Bad output fails fast at the boundary, not three layers deep.

Two-stage match

Cheap vector search before expensive LLM judgment

pgvector cosine similarity runs in-database to shortlist a top-N; the costly per-job gap analysis only runs on the survivors. Token economy by construction.

Grounding guard

Highlighted skills must be a strict subset of your CV

The CV-variant tool enforces set(highlighted) ⊆ profile.skills. The LLM can reorder and emphasize but can never fabricate a credential — the single most important safety property in the system.

JSON discipline

A shared preamble + fence stripper on every parsed prompt

Each prompt whose response is parsed prepends a JSON_ONLY_PREAMBLE; responses pass a fence stripper and parse with strict=False, because LLMs emit raw control characters in prose.

Injected deps

Dependency injection everywhere → 100% mockable tests

The full suite makes zero live calls; the LLM and scraper are always injected fakes. A demo is reproducible without the live endpoint.

Trust & control

Helpful with words — strict with facts.

GDPR and platform terms of service are first-class constraints, not an afterthought bolted on at the end.

✋

No auto-submit

The agent never files an application. It produces artifacts and a “ready to send” state; you click Apply on the real job page yourself.

⌦

Right to erasure

One call wipes your profile, scores, applications, and every generated .docx from disk. Deleting your account cascades the same rows.

🔒

Row-level isolation

Postgres RLS binds every request to your JWT, so the database — not just the app — guarantees you only ever see your own data.

Try it

Two commands to a running stack.

Bring your own Supabase project and a GWDG API key (both free-tier), then start it with Docker Compose or run the two services directly.

docker · fastest
# 1 · set Supabase + GWDG keys in .env
cp .env.example .env

# 2 · build & start both services
docker compose up -d --build

# open the app
→ http://localhost:3000

api (FastAPI :8000) + web (Next.js :3000), the same two-service layout used in deployment.

local dev · without docker
# backend
uv sync
uv run uvicorn job_agent.api.main:app

# frontend
cd frontend && npm install
npm run dev

# tests — all mocked, zero live calls
uv run pytest -q
